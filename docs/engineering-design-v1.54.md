# Writer's IDE — Engineering Design v1.54

**Status:** Active implementation design  
**Baseline:** Engineering Design v1.53

## Issue #8 — user and project keymap scopes

Command shortcuts are described by the central command registry, including stable command IDs and default shortcuts. The main menu declares Ctrl+/ as the preferred invocation and F10 as the interoperable fallback; plain `/` remains manuscript input. Effective shortcut labels appear in context help and the menu. Command dispatch continues through the shared registry dispatcher.

Keymaps load in two scopes: the per-user file at `$XDG_CONFIG_HOME/writers-ide/keybindings.toml` (or `$HOME/.config/writers-ide/keybindings.toml`) and the project file `.writers-ide/keybindings.toml`. Project bindings override a user binding for the same physical chord; other user bindings remain active. Invalid configuration is reported and falls back to valid defaults rather than preventing project startup. The CLI-style Tools commands can set, remove, list, and reset either scope. Writes are validated and atomically replaced. `keybinding-list` reports the effective configured commands and their winning scope.

The registry supplies default workspace and command shortcuts instead of a separate hard-coded workspace dispatch table. Commands requiring arguments open their registered prompts and use the common dispatcher. Issue #8's follow-on work adds editor, navigation, dialog, and menu contexts, one-to-four-chord sequences, project-over-user precedence, a 900 ms sequence timeout, and the in-terminal Keybinding Manager. The manager filters the command registry, captures sequences, shows and replaces conflicts, removes bindings, and resets a selected scope with confirmation. Ctrl+/ and F10 are rejected in every sequence position and remain accessible while a sequence is pending. Plain `/` remains manuscript input.

The terminal requests Crossterm's `DISAMBIGUATE_ESCAPE_CODES` keyboard enhancement flag at startup and pops it at shutdown. This is best-effort: terminals that support the protocol provide unambiguous modified-key events; older terminals, SSH paths, and multiplexers may ignore it, so Ctrl+/ remains terminal-dependent and F10 is the fallback. No capability response is currently surfaced to the user. Keymap files remain TOML under user XDG configuration and project `.writers-ide/`; bindings are validated both per-file and after scope merging so cross-scope prefix collisions are reported. The registry owns stable command IDs and a shared dispatcher, while many existing application operations remain legacy palette handlers behind registered command routes.

## Research documents in reference panes (Issue #13)

Reference sources use stable typed keys (`scene:<uuid>`, `research:<uuid>`, `character:<uuid>`, and `location:<uuid>`) rather than titles. Project-local session state stores all source keys and corresponding scroll offsets while retaining the older scene-only fields for session-file compatibility. Research references load their canonical local research body read-only; character and location references render read-only structured profiles from the story database. Reopening a missing source skips it and uses the existing stale-reference notice.

## Location profiles and hierarchy (Issue #13)

Migration 0032 adds a nullable parent-location foreign key and a description to each location. Parent references are restricted on deletion; self-parenting and ancestor cycles are rejected in SQLite triggers, including direct SQL writes. Profile changes update the location's full-text search projection. `ProjectStore::get_location` and `update_location` expose the typed profile, and application services forward those operations. The terminal supports `reference-location <uuid>` and restores these buffers by stable ID. The profile reference currently renders the parent UUID rather than resolving its display name; location editing and richer location-specific navigation remain open.

## Simultaneously visible reference buffers (Issue #13)

Every open scene-reference buffer is rendered at once in the editor's reference region. Wide terminals divide that region into columns; narrower terminals stack the references vertically. The active buffer remains identified in its border and retains its individual scroll offset. Existing next/previous commands select the active buffer, while focus and scroll commands continue to operate on that selection. Layout depends only on terminal dimensions and reference count; it does not alter stored scene order or buffer identity.

The reference region can open scene, character, location, plotline, research, timeline, project-search and compile-diagnostic buffers; they resolve again from typed stable IDs or reproducible query keys on session restore. `reference-follow-card` opens a live card for the editing scene; opening another scene refreshes the same pane while preserving its pane identity and scroll position. `reference-pin` freezes the current card. Pane headers show `follow` or `pinned`, and the mode is persisted with the stable source ID and restored on restart. `reference-layout auto|horizontal|vertical` chooses automatic responsive layout, side-by-side columns, or stacked rows; Ctrl+arrow resizing retains separate horizontal and vertical ratios. `reference-toggle` hides or shows reference panes without closing their buffers. Both settings are persisted in the session. The scene card is a read-only projection of typed scene metadata. Opening the currently edited scene with `reference-scene <uuid>` creates a second view over the same `editor` buffer; Ctrl-Tab swaps between independent cursor positions, PageUp/PageDown scroll the focused view independently, and edits/undo/save continue through the canonical scene buffer and durable journal. Both scroll offsets, focus and cursor state restore from the project session. Ctrl+PageUp/PageDown or the View menu cycles reference windows; Esc or Return to Writing restores editor focus. `window-swap` moves the editor to the reference group's opposite side and restores that arrangement on restart. Ctrl-G / Maximize Current Window expands the focused editor or reference pane, while Restore Window Layout returns to the saved split. Reopening another scene converts the prior pane back to a read-only reference snapshot. Buffers, orientation, split ratios, visibility, side order, focus and cursor state are stored in the project session. Ctrl-G focus mode hides the outline, reference buffers, header and footer while leaving the focused pane across the content area. General arbitrary pane rearrangement, editable structured entity panes, and richer per-pane selection state remain open under Issue #13.

Responsive split rendering now enforces a compact fallback without changing the saved layout: below 48 columns or 12 available content rows, the interface displays one focused pane full-size and shows a `Ctrl-Tab` hint. When the reference region is too short to give every open reference five rows, only the active reference is rendered until the terminal grows or the author cycles buffers. Hidden references, their buffers, scroll/cursor state and split ratios remain intact. Regression tests cover threshold decisions and active-reference selection; terminal resize tests continue to verify editor buffer persistence.

## Read-only scoped replacement preview (Issue #12)

`replace-preview` shares the existing Normal, Extended, and Regex transformation functions and scene-scope resolution with replacement. The CLI emits a JSON array of only changed scenes, including stable scene IDs, titles, source hashes, occurrence counts, original prose, and proposed prose. The TUI shows a bounded before/after preview and reads the active editor buffer when that scene is dirty; other scenes are read from canonical persisted files. Preview performs no writes and creates no snapshots. Applying remains an explicit `replace` action that saves per scene using optimistic hashes. Multi-scene application is not a single atomic transaction; recovery and selective rollback remain separate requirements.

## Session restoration for outline narrowing (Issue #2)

The existing atomic project-local session snapshot now records the narrowed chapter as a stable structural ID when the visible scene set exactly matches that chapter's current scenes. On reopen, it reapplies the filter only if the chapter still exists; stale chapter references are reported using the existing stale-reference notice. Split ratios were already persisted and remain clamped to safe terminal percentages. Because the current outline view is a flat scene list rather than a collapsible hierarchy, there is no expansion state to persist.

## Registry-backed command shortcuts (Issue #8)

The project-local `.writers-ide/keybindings.toml` accepts an optional `[commands]` table mapping modified key chords such as `"Ctrl+Alt+A"` to stable command-registry IDs such as `"view.analytics"`. Startup validates chords, command IDs, argument requirements, duplicate keys, and reserved editor/menu shortcuts before entering the TUI. On key input the TUI resolves the configured ID through the shared command registry, checks contextual availability, and dispatches the registered action. Bare printable keys are prohibited so manuscript input remains intact. Ctrl+/ and F10 remain reserved for the hierarchical menu. This increment does not yet provide an interactive binding editor or configurable bare keys; function-key workspace bindings retain their existing `[bindings]` format.

## Automatic local Git snapshots (Issue #11)

Projects may opt into an automatic local Git snapshot interval stored in `.writers-ide/git-snapshot.toml`. Intervals are integer minutes from 1 through 10080; an absent interval disables the feature. The terminal checks the policy periodically and invokes the existing application snapshot service, which reconciles pending manuscript journals and holds the SQLite writer barrier while generating and committing the deterministic metadata snapshot. No remote is contacted. The last successful check time is saved with a synced temporary file and atomic rename; unchanged projects advance the check time without creating empty commits. Failures remain visible in the terminal and do not advance the check time. Configure with `git-auto-snapshot PROJECT MINUTES|off`. This is a wall-clock best-effort policy, not a real-time guarantee; automatic snapshots only run while the terminal application is open. Selective historical structural/database restoration remains open.

## Explicit Git remotes and fast-forward retrieval (Issue #11)

Projects may configure named local, SSH, or Git-supported remotes with `git-remote-add`; `git-remotes` lists them. `git-back-up REMOTE BRANCH` first creates a journal-consistent local snapshot and then performs an ordinary non-forced push. `git-retrieve REMOTE BRANCH` snapshots local state before contacting the remote, requires the named branch to be checked out, fetches without changing project files, and refuses a divergent remote history. For a fast-forward, it validates an isolated reconstructed project, reconciles the tracked file set and SQLite metadata with the existing SHA-256 recovery journal, then advances the local branch ref using an expected-old compare-and-swap. The index is refreshed from the resulting commit without asking Git to overwrite the already-reconciled working tree. If the remote is unchanged, retrieval is a no-op after the local safety snapshot. Git's configured credential helper or SSH agent is used; remote URLs containing HTTP credentials or token-like query parameters are rejected. Push and retrieval are always explicit; no remote network activity occurs during ordinary saves or scheduled local snapshots. Tests use a local bare repository, including successful retrieval and divergence preservation. A filesystem/process failure between project-file application, Git ref movement, and index refresh can leave a recovery journal or a dirty Git index; the manuscript recovery journal protects canonical files, while a dedicated cross-process Git-ref transaction journal remains a hardening item. Divergent histories require user resolution outside this fast-forward workflow.

## Project-local custom LuaLaTeX templates (Issue #21)

`BookDesignProfile` optionally names a project-relative Pandoc template. Templates are only accepted for LaTeX/PDF rendering, canonicalized beneath the project root, and must be regular files; traversal and symlink escapes are rejected before starting Pandoc. The CLI and terminal already load project-local TOML profiles, so the same `--design-file=...` selector reaches this template option. A mocked renderer test verifies the resolved template argument without requiring an installed TeX toolchain. Template authors own their TeX constructs and must check their designs with their local Pandoc/LuaLaTeX versions; the built-in profiles remain the portable defaults.

## Terminal editorial conflict comparison (Issue #19)

When `review-merge` finds overlapping changes, it keeps canonical prose unchanged, opens the current scene, and renders each conflict's base, local, and reviewed lines in aligned columns in the editor's reference pane. A dirty buffer blocks the comparison instead of showing a stale local version. The same conflict ordering is used by `review-resolve`. The display truncates long individual lines to fit review columns; the complete conflict payload remains available from the CLI report, and whole conflict ranges are the supported decision granularity.

## Event dependency checks in processing (Issue #10)

The processing input now snapshots story events and explicit `precedes`/`requires` dependencies alongside scene intervals. The deterministic Continuity stage reports each recorded dependency as pass, fail, unknown, or skip using interval comparison; ambiguous and missing bounds remain unknown. Event/dependency data participates in the Continuity artifact fingerprint, so edits invalidate this stage without forcing unrelated stage outputs to rebuild. The report is a read-only projection and includes stable event IDs as evidence.

## Browser event chronology planning (Issue #17)

The loopback browser planner now presents event time bounds and source labels with an edit action. The form accepts exact ticks, unknown, approximate, and bounded interval syntax and posts to `/api/events/{id}/time`; the route delegates to `WriterApp::update_story_event_time`. Values are validated by `StoryTime`, event identity/title/description are retained, and no scene prose route is added. Existing host/origin checks apply to the write. Broader browser parity and interactive multi-event timeline manipulation remain open.

## Event chronology editing (Issue #9)

Event story-time bounds can now be updated independently from title and description through an application/storage operation that only updates start, end, precision, and source-time text fields. The terminal `event-time-set` accepts exact ticks, unknown `?`, approximate `~nominal,lower,upper`, and bounded `lower..upper` values. The CLI `event-time-set` offers the same tick formats. This keeps event identity, descriptive metadata, and manuscript order unchanged when chronology is revised. Timeline drag editing and fictional-calendar conversion remain open.

## Explicit editorial conflict decisions (Issue #19)

`story_import::resolve_three_way_merge` accepts one ordered `Base`, `Local`, or `External` choice per conflict returned by the three-way merge. Non-conflicting edits remain in the result. `WriterApp::resolve_review_text` reloads the current scene hash and saves with the standard optimistic journal, so a changed local file fails rather than being overwritten. CLI `review-resolve` and the terminal command accept comma-separated choices in the order shown by `review-merge` conflict JSON. The operation is whole-conflict-range resolution; interactive side-by-side comparison, character-level hunk editing, and Word comment anchoring remain open.

## DOCX staged text fidelity (Issue #6)

DOCX inventory now parses paragraph events with `quick-xml`, identifies Heading/Title paragraph styles, preserves tabs and explicit line breaks, resolves XML named and numeric character references, and rejects malformed XML inside a paragraph rather than producing a partial stage. Bold, italic and strike runs are emitted as escaped Markdown spans, including text split across XML entities and tab/break boundaries. Underline, font color, highlight, run fonts, capitalization and hidden-text styles are reported when detected; hyperlinks retain anchor text but report their unpreserved destinations. Tables and drawings retain the existing loss reporting. The parser remains read-only and fingerprints original archive bytes. Comments, multi-file import mapping choices and full rich-text fidelity remain open.

## Project-local custom book-design profiles (Issue #21)

`BookDesignProfile` is a versioned TOML value model. It validates a bounded document class, paper size, class options, geometry token characters, font-size range, line-spacing range, and safe font-family names. Optional main, sans-serif, and monospaced families, `plain`/`headings`/`empty` page styles, and section numbering are passed to Pandoc for both direct LaTeX and PDF output. Font availability remains the selected LuaLaTeX installation's responsibility. CLI and terminal `compile-format` accept `--design-file=<project-relative-path>`; canonicalization rejects traversal and symlinks that escape the project. Preset `BookDesign` values remain supported and convert to equivalent profile values. Profiles retain the isolated temporary workspace, TeX/log sidecars, and compile source maps. `templates/book-design/compact-trade.toml` is a portable example. More extensive chapter ornament/layout choices remain the responsibility of a project-local TeX template.

## Browser graph visualization (Issue #17)

The browser planning page renders the existing shared `/api/plan` projection into an inline SVG graph. Stable entity UUIDs identify structural groups, scenes, characters, plotlines, locations and events; persisted relationship edges are drawn between available nodes. Scene nodes navigate to the read-only scene review pane. The browser still mutates only the planning operations exposed by its API, and no browser route writes manuscript prose. This is a visualization of the shared graph data rather than a second graph store. Full terminal workspace parity, query editing and broader Story Bible/issue editing remain open.

## Phase 3 production refinements

`story_document::CompileFormat` includes in-process plain text and Markdown alongside LaTeX, HTML, EPUB, DOCX and PDF. Plain text renders the Compile IR Markdown with pulldown-cmark into UTF-8 text, preserving heading labels, paragraph breaks, ordered/unordered list items, table cells and code while removing Markdown markers; no Pandoc process is needed. CLI, processing recipes and terminal compile commands use the `text`/`.txt` format. The sidecar still maps source entities and source byte ranges in the canonical Compile IR Markdown stream; it does not claim offsets into the transformed plain text. PDF uses the generated LaTeX as its single source: the renderer first generates `compiled.tex` from the shared Compile IR and selected book-design profile, then invokes LuaLaTeX once on that exact file and returns its PDF. It no longer runs a separate Pandoc PDF render whose output could disagree with the preserved TeX. Successful renders return `compiled.tex` and `lualatex.log` as auxiliary artifacts; failed runs include available LuaLaTeX log text in the renderer error, which is recorded in Compile Results. CLI compile, edition and watch commands, and the terminal compile command publish successful TeX/log artifacts next to the requested PDF using the existing staged publication path. Source maps continue to describe renderer-neutral Compile IR offsets, not visual page positions. Built-in fixed profiles cover trade paperback, hardback, submission manuscript, nonfiction, and technical/academic layouts. Publication diagnostics additionally report likely draft placeholders (`TODO`, `FIXME`, `[INSERT`, and `Lorem ipsum`) as a source-entity-linked warning without modifying prose.

Successful LuaLaTeX log parsing adds structured diagnostics for missing glyphs, overfull boxes, underfull boxes, unresolved references, and font/document errors. Findings retain generated-file locations in `lualatex.log` with one-based log line numbers and appear in Compile Results alongside canonical-source diagnostics. They do not block a completed build and do not claim a source passage mapping. Missing toolchains and fatal renderer errors remain operational failures; a failed renderer exposes captured log text in its error record.

DOCX editorial review can now derive an accepted or rejected text view of `word/document.xml` tracked-change insertion/deletion elements. `review-inspect` exposes insertion, deletion and comment metadata; `review-docx` submits the selected accepted/rejected view with the author-supplied base through the existing three-way merge and optimistic journal save. It never modifies the DOCX source. Comment range anchoring and interactive selection/resolution of individual conflicts are still open.

The Editor workspace now supports character-indexed text selection, highlighted selection rendering, multiline copy/cut/paste in the application's internal clipboard, and Shift+Arrow selection. Uppercase/shifted text is accepted, and horizontal movement crosses line boundaries. Selection and clipboard state are transient UI state; only resulting manuscript text is persisted, through the existing optimistic durable save path. ## Named Compile configurations and managed artefacts (Issue #7)

Compile configurations are project-local, versioned `EditionRecipe` TOML files under `.writers-ide/compile-configurations/`. Stable lowercase slugs identify configurations; the initial presets are `submission` (DOCX), `ebook` (EPUB), `paperback` (PDF), `proof` (manuscript PDF), `plain` (TXT), and `markdown`. Each preset writes beneath `exports/compile/<slug>/`. The application API is shared by the CLI `compile-config` command and the terminal Compile command registry.

`compile-config list|results|create|run|all|rebuild|clean` provides profile management. A managed-output manifest in `.writers-ide/compile-artifacts.json` records each output, source map, and renderer sidecar by relative path and SHA-256. Run refuses to replace a pre-existing untracked file or a tracked artifact whose content changed outside Writer's IDE. Rebuild is an explicit replacement action. Clean requires `--yes`, preflights the full set, and removes only hash-matching manifest-listed regular files within that configuration's managed output directory. Symlinks and path traversal are rejected; canonical manuscript files are never eligible for cleanup. Each successful or failed run writes a versioned JSON result record in `.writers-ide/compile-results/`, including elapsed time, generated outputs, warnings, and failure detail; recent records are available in the CLI and terminal.

The existing `compile <format>` and `compile-format` commands remain available for explicit one-off outputs. They share the staged publisher, source-path protection, and collision refusal policy, but their generated outputs are not entered in the named-configuration manifest. `compile-edition` also uses the shared publisher and requires `--overwrite` to replace existing files. ODT and RTF use Pandoc's native writers; AZW3 uses optional Calibre conversion, and MOBI is explicitly legacy and converter-dependent. Ordinary failures during a multi-file publication roll back earlier replacements; process/power interruption is reconciled by the durable output-set journal described in the next section. A local HTML manuscript preview is now available from the browser view. The full Issue #7 diagnostic-results pane, per-rule severity policy from #10, EPUB/PDF viewers, all requested backends, configurable content-control fields, and complete language/typography acceptance remain open.

## Crash recovery for compiled output sets (Issue #7)

One-off and managed Compile publication now share a durable output-set journal at `.writers-ide/recovery/compile-publication.json`. Before replacement, every new artifact is written and synchronized to a uniquely named temporary file beside its destination. Existing outputs are copied to same-directory rollback files and synchronized. The journal then records the project identity, transaction UUID, each target/staging/backup path, and the SHA-256 of previous and proposed contents; the journal file and recovery directory are synchronized before the first target changes. Each target is replaced by same-filesystem rename and its parent directory is synchronized. After every file has the proposed hash, a durable `Committed` journal state is written. Only then are rollback copies removed; the journal is removed and its directory synchronized last.

On project open, recovery inspects every pending target. A `Prepared` transaction is rolled back only if each target is still at its previous hash or at the proposed hash and every required backup matches; committed transactions are cleaned only if all targets still match their proposed hashes. Recovery is idempotent if interrupted. A third hash, missing required backup, project-ID mismatch, or invalid path leaves the target, staged copy, backup, and journal untouched and exposes a conflict notice in the TUI. CLI `compile-recovery <project> status|retry` reports the notice or retries after the author has resolved the conflicting file. A conflict does not permit a new compile to replace outputs. Relative paths inside the project survive relocation; absolute one-off destinations remain absolute.

Fault-injection tests cover interruption after durable intent, midway through replacement, and after the commit marker; they verify rollback/cleanup, relocation, and preservation of externally changed outputs. File contents are synchronized before intent, and destination directories are synchronized after rename. The implementation assumes same-filesystem rename is atomic per file and that the target filesystem honors file and directory `fsync`; it does not make a multi-file set appear atomically to concurrent readers. A crash before the durable intent may leave uniquely named staging/backup files, but original destinations remain untouched. Windows rename semantics and automatic orphan-file cleanup remain open portability work.

## Plot Grid matrix

The Plot Grid workspace now derives a read-only matrix from `analytics_dataset`: scenes are rows in manuscript order, plotlines are columns, and a filled marker indicates scene membership. Chapter titles are resolved from structural nodes; unplaced scenes are labelled explicitly. The matrix reads canonical relationships and cannot change them. The app-level regression fixture verifies that an assigned plotline appears in the matching scene row.

The Characters workspace now derives a read-only scene-by-character matrix. Cells distinguish POV (`P`), major (`●`), minor (`○`), off-camera (`o`), mentioned (`m`), and no recorded participation (`·`). It reads application analytics and remains a projection; editing relationships continues through application services. A regression check verifies that a POV link appears with its role marker.

## Passage anchor revalidation

Scene saves revalidate passage anchors inside the same SQLite transaction that commits the manuscript hash and search index, including recovery after an atomic file replacement. A unique exact quote match is reattached automatically. Repeated matches are scored against saved prefix/suffix context and are reattached only if one candidate has a unique non-zero best score. Missing passages become `broken`; ambiguous repeated passages become `needs_review`. The stable anchor UUID is retained in all cases. `anchors` lists a scene's anchor states and `anchor-move <anchor-uuid> <start-byte> <end-byte>` explicitly reattaches an anchor after the author selects the correct passage. The operation validates UTF-8 boundaries and exact quote identity. The CLI provides `anchors` and `anchor-move` equivalents.

Tests cover unique relocation, context ambiguity, removed passages, explicit reattachment, invalid offsets and recovery after rename-before-database-commit. Anchor updates participate in the same transaction as recovered manuscript metadata so the durable journal cannot commit text while leaving anchor state silently current at stale offsets.

## Project-wide full-text index

Migration 0005 adds a rebuildable FTS5 index over a typed `project_search_content` projection. It indexes scene titles, synopsis, purpose, goal, outcome, status and manuscript text; character and location names; plotline names; event titles/descriptions/source time; research titles/bodies; issue titles/status; and imported reading titles/text. SQLite triggers keep the projection and FTS table current. Search returns typed entity kind/ID, title and excerpt, with deterministic ranking ties. `rebuild_project_search_index` recreates the virtual index from its ordinary projection table.

`search-all` is available in the CLI and terminal command palette. Terminal results navigate to their underlying story entity or reading document. Existing scene-only and reference-only search APIs remain available. The storage tests cover initial migration from schema v4, incremental updates for prose and metadata, typed results, empty queries, result limits, and index rebuild.

Migration 0006 adds custom scene-field values to that projection. Text, long text, integer, decimal, boolean, enum, and entity-reference scalar values are searchable. Triggers recompute a scene's indexed projection when a custom value is inserted, updated, or deleted, and when scene prose or core metadata is subsequently updated. Existing custom-field values are included when migrating. Tests verify custom value updates, deletion, and that later manuscript saves preserve the custom metadata in the index.

## Scene planning commands

The terminal command palette now edits core scene purpose fields through `scene-field <scene-uuid> <synopsis|purpose|goal|outcome> | <text>`. `character-link <scene-uuid> <character-uuid> <pov|major|minor|off_camera|mentioned>` creates typed participation. `event <title> | <source-time>` creates story events and `event-link <scene-uuid> <event-uuid> [relationship]` associates them with scenes. Issues can be linked through `issue-link <scene-uuid> <issue-uuid>`.

The terminal doesn't normalize incomplete or excessive allocations. Tests exercise the commands and verify role/relationship/metadata persistence through the application API.

The issue tracker now supports status transitions through `issue-status <issue-uuid> <open|in_progress|resolved|deferred|closed>` in the terminal command palette and CLI. Invalid statuses and missing issue IDs are rejected by the service/storage boundary; updates refresh the indexed issue status. The terminal integration test creates, links, and transitions an issue, then checks its persisted status.

The Reading command palette lists annotations and bookmarks with stable zero-based indices. `annotation-jump <index>` and `bookmark-jump <index>` navigate to their stored byte offsets without changing the imported source. Navigation validates that offsets are within extracted UTF-8 text and land on a character boundary, then updates the reading pane's scroll position and focus. ## In-place reading annotation rendering

The Reading source pane renders current annotations over the extracted UTF-8 text without changing that text or the imported source file. Highlight annotations use yellow background with black foreground; note annotations use cyan underlining. Stale, broken, or otherwise non-current annotation records are not applied to the passage. Invalid, out-of-range, or non-character-boundary offsets are ignored defensively. Rendering uses stored byte anchors and keeps annotation records separate from source content. The terminal integration test verifies that a saved highlight decorates the expected passage while annotation/bookmark navigation continues to work.


## Analytics workspace report

The terminal Analytics workspace now displays all scene rows in the character appearance heatmap, with participation roles distinguished as POV, major, minor, off-camera, and mentioned. ### Outline synchronization and entity mentions

### Alternate manuscript assemblies

Migration 0015 adds `manuscript_assembly` and `assembly_item`. An item references one scene or content unit by stable ID, has an assembly-specific non-negative integer position and inclusion flag, and may not duplicate the same source twice in one assembly. A source may belong to multiple assemblies. Reordering uses a transaction and temporary integer positions to avoid immediate unique-index violations; canonical `scene_placement` is never updated. The application compiles included items in assembly order to a renderer-neutral Compile IR and Markdown export. The terminal exposes a Manuscript Assemblies workspace, per-assembly content addition, filtering, ordering, Markdown compilation and continuous resumable draft editing. Assembly editing uses project-local JSON drafts under .writers-ide/assembly-drafts/. Each draft records project/assembly identity, stable scene IDs, each scene's expected original SHA-256, and the proposed UTF-8 text. Draft updates use synced temporary files and atomic replacement. Commit preflights every source hash before saving any scene; each changed file is then written through the existing per-scene optimistic journal. If interrupted between files, retry recognizes scene files already at the proposed hash and resumes only the remaining old-hash files. Any third hash is treated as an external conflict: no divergent scene or draft is overwritten. This protocol makes multi-file persistence recoverable, though visibility across files is not atomic during a commit. In the terminal, :assembly-edit <assembly-uuid> opens one continuous buffer with stable, draft-specific scene marker lines; Ctrl-S validates order/identity, atomically persists all proposed segment text as one draft update, then commits through per-scene journals. Broken, missing, or reordered markers prevent all manuscript writes. :assembly-drafts lists pending work and :assembly-resume <draft-uuid> reopens it after interruption. CLI supports draft create/list, text replacement from UTF-8 files and commit/resume.

Optional writing statistics are disabled by default and controlled by writing-stats on|off|report|reset. When enabled, the terminal stores only aggregate Unicode scalar counts for typed versus pasted input and successful saves in .writers-ide/session.json; no text, key sequence, timing, or scene-level history is captured. Counts survive session restoration, can be reset explicitly, and stop changing when disabled.

### Search and replace foundation (Issue #12)

Search modes share `story_core::find_matches_with_options` and `replace_matches_with_options`, returning UTF-8 byte ranges and preserving literal text semantics. Extended mode decodes only newline, carriage-return, tab and escaped backslash; regex mode uses Rust `regex` (no look-around or backreferences in the search pattern), supports `$1`/`${name}` replacement references, and treats `^`/`$` as line anchors. Options control case sensitivity and Unicode word boundaries. CLI and terminal expose current-scene, open-buffer, selected-scene, explicit scene, chapter, assembly, and all-project scopes. Assembly scope follows selected assembly order and excludes disabled items. In the terminal, Space marks scenes in Outline, Cards or Search for a selected-scene scope; the open-buffer scope includes the active scene, scene reference buffers and assembly-draft scenes, including unsaved text. The keyboard-driven bottom panel opens with Ctrl-F for find or Ctrl-H for replace, defaults to Normal, cycles Normal/Extended/Regex with F2, cycles scopes with F4, toggles case sensitivity with F6 and whole-word matching with F7. Search results appear in the editor's scene pane with scene, line and context; F3/Shift-F3 navigate matches. Replace Enter stages a read-only preview listing each affected scene and its original/proposed text. F3 cycles preview matches, F6 toggles one match, F8 toggles a scene, F5 applies selected replacements, and Esc cancels. F9 replaces the next current-scene match as one editor undo step. The Edit menu also exposes Find in All Open Files, Find in Project, definition lookup, references, return position, preview/apply/cancel and undo-last-scoped-replacement.

Space-selected scenes and open-buffer scopes include unsaved editor and assembly text. An open assembly scene is searchable, but replacement is blocked until its draft is saved and reopened as scene files; this avoids writing a representation that has no per-scene durable file state. Find history persists the last pattern, replacement, case and whole-word choices plus up to 50 distinct successful queries (newest first) under `.writers-ide/find-session.json`. F11/F12 are default older/newer query shortcuts; `search.history-older` and `search.history-newer` are registered commands and can be rebound through project keybindings. History navigation returns to the in-progress query and does not reorder saved history. Each opening resets to Normal mode and current-scene scope so an earlier advanced mode or broad scope is never silently reused. Pattern entry remains literal by default; F2 cycles Normal, Extended and Regex modes, whose current Rust-regex syntax and capture replacement behavior are described in the user help.

Terminal multi-scene replacement writes a durable group intent under `.writers-ide/recovery` before saving the first scene. It records each scene's prior text/hash and proposed text, then saves each file through the existing manuscript journal. Startup recovery first classifies every target: it automatically restores the prior versions only if every file is either unchanged or exactly at its proposed text. If any file diverges, recovery preserves all content and retains the group record for inspection. After successful apply, a one-operation undo record is stored; Ctrl-Z uses it when the editor's local undo stack is empty, and the Edit menu exposes the same action. Undo itself uses the group journal and hash checks. If the project already has `.git`, Writer's IDE takes a pre-change Git snapshot. Ordinary write failures trigger immediate rollback; interrupted writes resume recovery on the next terminal open. The filesystem does not provide a cross-file atomic rename, so the guarantee is crash-recoverable rollback rather than a simultaneous all-filesystem commit. CLI `replace-apply` revalidates every source hash, writes its own durable group intent, rolls back interrupted/failed batches only when every target is unambiguous, and preserves divergent versions with an explicit recovery notice. `replace-recover` retries that inspection/recovery and `replace-undo` performs a hash-checked, journalled one-step undo. A pre-change Git snapshot is created when the project already has Git. `tags <name>` rebuilds definition results from stable entity IDs, titles and character aliases; `refs <name>` searches raw prose and labels those hits as textual references, not participation. `tags-export` writes an Emacs TAGS file and a generated Markdown symbol index under `.writers-ide/tags`; aliases are emitted as tags and the index includes stable IDs and source paths. TAGS offsets target the generated index rather than opening structured database records. A separate confirmed-mention workflow navigates to author-confirmed passage references and distinguishes them from actual character participation. A location stack supports return after jumps. Continuously maintained symbol indexing, Ctags output and richer semantic-reference navigation remain deferred.

## Issue #11 — Restore an archived scene under its original identity

`restore_archived_scene_from_git(commit, scene_id)` reconstructs and validates the selected historical project in an isolated temporary directory. Existing character, plotline and event relationships remain attached to that scene identity. ## Issue #11 — Preview and transactionally restore a full project snapshot

`preview_git_restore(commit)` validates the requested commit by rebuilding its deterministic SQL snapshot in an isolated temporary project, checking foreign keys/project invariants, and matching the immutable current project ID. `GitRestorePreview` reports changed, added and removed Git-owned paths compared with `HEAD`, plus pending working-tree changes. Preview does not change the current project or create a commit. CLI `git-restore-preview` emits this DTO as JSON. The terminal File menu exposes the same preview and shows path-level changes.

`restore_git_snapshot_in_place(commit)` requires an explicit `--confirm` in the CLI/terminal command. It previews before mutation, then resolves pending manuscript journals and takes a safety snapshot of current state. It reconstructs and validates the requested project, prepares replacement and backup bytes under `.writers-ide/recovery`, writes a SHA-256 journal durably, closes/checkpoints SQLite, replaces only Writer's IDE tracked files plus `story.db` with same-filesystem atomic file operations, reopens/migrates/validates the database, then marks the journal committed. Untracked project files outside the versioned set remain untouched; tracked current-only files are removed but retained in the safety snapshot. `ProjectStore::open` rolls back an incomplete restore by comparing current file hashes to the old/proposed hashes. A third, divergent hash is treated as an external conflict: opening fails visibly and both the conflict and recovery copies are preserved for explicit repair. Tests cover preview read-only behavior, pending working-tree changes, confirmation, complete manuscript/metadata restoration, recovery after an interrupted file-set application and conflict preservation. Versioned snapshot compatibility is validated by reconstructing through current schema migrations before in-place changes.

The restore transaction provides atomic replacement per file with durable all-file rollback, not a single filesystem-wide atomic visibility point. Forced termination during application may leave a mixed tree until the next project open performs recovery. The preview lists file paths rather than rendering semantic prose/metadata diffs, and external untracked content inside versioned directories is included in the pre-restore safety snapshot before any selected-commit deletion.

## Issue #8 — Contextual key sequences and keybinding manager

Context tables use `[contexts.editor]`, `[contexts.navigation]`, `[contexts.dialog]`, and `[contexts.menu]`; keys are whitespace-separated modified chords, limited to four per sequence. Prefix collisions are rejected within one keymap and again after user/project merging. Project scope replaces an exact user sequence; nonconflicting user sequences remain effective. A 900 ms timeout expires an unfinished sequence when another key arrives; a nonmatching key cancels the prefix and is reprocessed normally. The manager opens through registered command `settings.keybinding-manager`, searches registry IDs and labels, switches context and scope, captures or removes bindings, confirms replacements, and resets only the selected scope after confirmation. Multi-chord global bindings remain unsupported; use a context map. Crossterm keyboard enhancement is requested best-effort rather than capability-probed, and F10 remains the fallback where Ctrl+/ cannot be encoded.
