# Writer's IDE — Engineering Design

**Version:** 0.2  
**Status:** Approved Phase 1 design  
**Basis:** Software Requirements Specification 0.1

This document turns the SRS into an initial Rust domain model, SQLite schema, module boundaries, service APIs and terminal navigation model. It is intended to guide a small vertical slice and early importer prototypes. It does not lock the project into a specific TUI editor, desktop framework, rich-text format or Scrivener version.

## 1. Design decisions

1. A scene is a durable domain entity. Its identity does not depend on its chapter, manuscript position or file name.
2. A scene's manuscript placement is represented by a chapter membership and an explicit order key. Chronology is separate optional data.
3. Relationships such as scene-to-plotline and scene-to-character use join entities so role, attribution and provenance can be recorded.
4. SQLite stores structured data and the canonical ordering. Prose is stored as UTF-8 Markdown files, addressed by a stable scene UUID in the database.
5. All mutations pass through application services and database transactions. Frontends do not issue domain SQL directly.
6. Importers first produce a read-only inventory and a mapping plan. Committing an import creates a new project and records source provenance; it never mutates the source.
7. Fictional chronology uses signed 64-bit integer ticks and explicit precision/uncertainty; calendar interpretation is a separate project-level concern.
8. Each project directory owns exactly one SQLite database. Project identity is immutable and checked against `project.toml`.
9. Manuscript writes use a durable journal and optimistic SHA-256 checks; recovery preserves ambiguous versions for user resolution.
10. Scene metadata has typed core properties and normalized relationships, with a typed custom-field system for additional project-specific fields.
11. Import provenance is recorded from the first migration, even before source-specific importers exist.

## 2. Workspace and crate responsibilities

Initial workspace (crate names are provisional):

```text
writers-ide/
├── Cargo.toml
├── crates/
│   ├── story-core/       # IDs, domain types, invariants, value objects
│   ├── story-storage/    # SQLite repositories, migrations, file store
│   ├── story-app/        # reusable application use cases
│   ├── story-import/     # inventory and mapping interfaces; adapters later
│   ├── story-analysis/   # word budgets, plot/character matrices, reports
│   ├── story-continuity/ # deterministic diagnostics over supplied facts
│   ├── story-export/     # compilation and structured reports
│   ├── story-templates/  # project and planning templates
└── apps/
    ├── cli/              # Phase 1 engineering CLI
    └── terminal/         # Ratatui/Crossterm frontend; Phase 2
```

Dependency direction: `story-core` has no dependency on persistence or presentation. Storage, analysis, continuity, import and export depend on core. `story-app` composes use cases over storage and is reusable by both frontends. UI widgets call use cases, not repositories. Avoid adding further crates until a boundary or reuse need is demonstrated.

## 3. Domain model

### 3.1 Identity and common fields

Externally addressable entities use UUIDs generated by the application and serialized as lowercase hyphenated strings. IDs are never derived from names, order or paths. Database rows use `TEXT` IDs to keep import/export and debugging straightforward. Every mutable primary entity has `created_at` and `updated_at` audit timestamps stored as UTC Unix seconds rendered as decimal text; they are not story chronology.

Core entity types:

| Entity | Purpose |
|---|---|
| Project | Project settings, title, target and schema-independent preferences |
| StructuralNode | Section/act, chapter or future grouping in the manuscript tree |
| Scene | Stable narrative unit, metadata and lifecycle state |
| Plotline | Main plot, subplot or other author-defined thread |
| Character | Person or other agent represented in the story |
| Location | Place hierarchy and descriptive information |
| StoryEvent | Fictional-world occurrence, independent of its representation in prose |
| ResearchItem | Note or reference with links to story entities |
| Issue | Author-managed question or task |
| CustomFieldDefinition / CustomFieldValue | Project-defined typed metadata |

Other entities (objects, world rules, relationships, knowledge claims, snapshots, attachments) are planned extension points and should not be flattened into scene text. Add them with their own IDs and join tables when implementing those phases.

### 3.2 Manuscript structure and scene identity

The initial hierarchy is `Project → Section → Chapter → Scene`, with Section optional. `StructuralNode` supports configured levels while retaining an explicit kind for common operations. A scene is not a structural node: it is linked to exactly one chapter at a time through `scene_placement`. This makes movement explicit and keeps the scene's stable identity independent of placement.

For the first release, a scene has one current manuscript placement. If alternate versions or multiple manuscript occurrences are later required, introduce occurrence/variant entities rather than duplicating the scene row. Reordering uses non-negative integer `position` values. Unique indexes cover both non-root siblings and roots (SQLite UNIQUE permits repeated NULLs, so roots use a partial unique index). Moves compact positions transactionally using a two-phase offset above the existing maximum, avoiding transient uniqueness conflicts. Structural moves reject cycles.

`StructuralNode` may carry an optional target word count. Scene target is stored on `Scene`; actual words are calculated from the prose file and cached with its content hash. Parent actual totals are derived, not authoritative stored values.

### 3.3 Scene relationships

- `scene_plotline(scene_id, plotline_id, role, share_basis_points)` allows multiple plotlines and exact author-attribution inputs; policy is supplied to analysis/use cases.
- `scene_characters(scene_id, character_id, participation_role, notes)` distinguishes POV, major, minor, off-camera and mentioned participation.
- `scene_events(scene_id, event_id, relationship_kind, notes)` is many-to-many: one scene can depict several events and an event can span scenes.
- Scene starting and ending locations are nullable references on the scene (or a dedicated location participation table if more granular movement is needed).
- Plot points and story points should initially be records in a shared `narrative_beats` table with a required `kind`; they may link to a scene, plotline and/or event. This avoids confusing them with whole-world StoryEvents.
- Tags use normalized tag records and join tables. Custom fields use typed definitions and values, with validation at the application boundary.

No join row implies an analytical judgment. For example, multi-plot membership records author attribution; charts state whether they use overlap, equal split or author proportions.

### 3.4 Story time

Canonical time is signed 64-bit integer ticks (`i64` in Rust, SQLite `INTEGER`), where one tick is one second from the project-defined story epoch. Relative story days are 86,400 ticks; a project may label the epoch and calendar without imposing Gregorian semantics. Negative ticks are valid. Null means unknown; zero is a known epoch value. `StoryTime` stores an optional nominal tick, precision (`exact`, `approximate`, `bounded`, `unknown`) and optional inclusive lower/upper tick bounds. Exact values require equal bounds; bounded values require ordered bounds and may omit a nominal tick, while any present nominal must lie within bounds. Start/end are separate values and duration uses checked subtraction and can return uncertainty bounds. Comparisons between disjoint intervals are ordered; overlapping or insufficiently bounded intervals return `Ambiguous`. No float or SQLite date arithmetic is used. Import retains source text alongside normalized values; unparseable/ambiguous source values remain unnormalized.

### 3.5 Prose storage and durable write protocol

Each scene file is `manuscript/<scene-uuid>.md`; all managed paths are relative and canonicalized beneath the project root. `scene_content` stores the committed SHA-256, byte length and generation. Every save has a UUID transaction ID and expected prior hash. The protocol is: (1) compare current target hash to expected committed hash; (2) write and `sync_all` a same-directory temporary file; (3) write and `sync_all` a second candidate under `.writers-ide/recovery/<transaction-id>/candidate.md`; (4) sync both directories; (5) transactionally insert a durable `PREPARED` journal row with old/new hashes, temp/candidate/target paths and generation; (6) recheck the target hash immediately before replacement; if it changed, preserve both and report conflict; (7) atomically rename temp over target; (8) sync target directory; (9) transactionally update `scene_content` and journal to `DB_COMMITTED`; (10) delete the journal durably, then remove candidate/temp and sync directories. Journal completion is cleanup-safe and idempotent.

On recovery, a matching target/new hash means finish metadata commit; matching target/old hash plus valid temp/new hash means perform replacement and commit; incomplete temp with old target means discard only the temp/journal after recording recovery; missing or unexpected target hashes, or a third external version, are conflicts. Preserve divergent target and candidate under `.writers-ide/recovery/<transaction-id>/`, record/report the conflict, and require explicit resolution. Never infer that an external version should be replaced. Crash before journal intent leaves only an orphan temp, which startup quarantines or removes only after confirming it is not referenced. Recovery itself is idempotent. Hash checks are optimistic concurrency control for both internal and external edits.

Durability assumes a local filesystem that provides atomic same-filesystem rename and honors file and directory `fsync`; some network/removable filesystems may not. The application reports reduced durability when directory sync is unsupported. Backups use SQLite's online backup API for a consistent database snapshot and validate copied manuscript hashes against that snapshot before publishing the staged backup directory. Preserve imported formatting artifacts when Markdown conversion is lossy.

Write states and recovery outcomes:

| Durable state at interruption | Startup action |
|---|---|
| Partial temp, no journal | Keep committed target; remove recognized orphan temp after confirming no journal references it |
| Synced temp/candidate, no journal | Keep committed target; remove recognized orphan artifacts |
| `PREPARED`, target matches old hash, temp matches new hash | Atomically replace target, sync directory, commit new SQLite metadata |
| `PREPARED`, target matches new hash | Commit new SQLite metadata; clean journal/artifacts |
| `PREPARED`, target matches old hash, no complete temp | Keep old target; discard intent/artifacts |
| Any pending intent with third/missing target or hash mismatch | Preserve target and candidate under recovery; record conflict and await author choice |
| `DB_COMMITTED`, target matches new hash | Remove journal, then remove candidate and sync directory |
| Journal removed, cleanup interrupted | Treat manuscript/database as committed; remove only recognized unreferenced temp/candidate artifacts |

The durable candidate remains available through the pending-journal interval so an external edit after replacement cannot erase the prepared version before recovery. Conflicts keep both the external target and candidate. All transitions are idempotent; a crash during recovery is handled by re-evaluating hashes on the next startup.

## 4. SQLite schema outline

Use SQLite foreign keys (`PRAGMA foreign_keys=ON`), WAL mode, `synchronous=FULL`, busy timeout, and numbered migrations in a `schema_migrations` table. Every connection must enable foreign keys. Store schema version separately from project content version. Use indexes for joins, search and order. FTS5 is optional at startup and must have a documented fallback if unavailable.

Migration 0001 is implemented in `crates/story-storage/migrations/0001_initial.sql` and loaded by `story-storage`; it is the Phase 1 schema source of truth. It creates the following core tables: `project`, `structural_node`, `character`, `location`, `plotline`, `story_event`, `scene`, `scene_placement`, `scene_content`, scene relationship joins, typed custom-field definitions/values, `write_journal`, `write_conflict`, import provenance tables, and `schema_migrations`.

Critical constraints include:

```sql
CREATE TABLE project (
  singleton INTEGER PRIMARY KEY CHECK(singleton=1),
  id TEXT NOT NULL UNIQUE, ...
);
CREATE UNIQUE INDEX structural_root_position
  ON structural_node(position) WHERE parent_id IS NULL;
-- non-root siblings additionally use UNIQUE(parent_id, position)
CREATE TABLE scene_placement (
  scene_id TEXT PRIMARY KEY REFERENCES scene(id) ON DELETE CASCADE,
  chapter_id TEXT NOT NULL REFERENCES structural_node(id) ON DELETE RESTRICT,
  position INTEGER NOT NULL CHECK(position >= 0),
  UNIQUE(chapter_id, position)
);
-- Triggers reject non-chapter scene destinations, retyping populated chapters,
-- deleting nodes with children/scenes, structural cycles and project identity edits.
CREATE TABLE scene_plotline (
  scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  plotline_id TEXT NOT NULL REFERENCES plotline(id) ON DELETE RESTRICT,
  role TEXT NOT NULL,
  share_basis_points INTEGER CHECK(share_basis_points BETWEEN 0 AND 10000),
  PRIMARY KEY(scene_id, plotline_id)
);
```

All position columns are non-negative integers. Root sibling uniqueness is a partial index because SQLite permits repeated NULLs under an ordinary unique constraint. Reorder operations use an `IMMEDIATE` transaction and two disjoint positive staging ranges before final compaction, avoiding transient uniqueness failures while satisfying non-negative checks. The database trigger and service layer both enforce chapter-only placement and acyclic structure. `story_event.time_*` and scene start/end values use SQLite `INTEGER` ticks (Rust `i64`); precision, lower/upper bounds and source representation are explicit. `scene_plotline.share_basis_points` uses basis points, never floating point.

Additional tables deferred beyond Phase 1 include: `narrative_beat` and its joins, normalized tags, research/issue entities, character relationship/knowledge, story objects/transfers and world rules. Import provenance tables are part of migration 0001. FTS indexes are a later, rebuildable addition.

Do not use polymorphic `entity_type/entity_id` foreign-key pairs for core relationships where a real foreign key can be maintained. For cross-type research links, use a typed link table per target kind or accept and validate a polymorphic edge in the application layer with explicit integrity checks.

## 5. Rust API boundaries

The domain model exposes value types and invariants. Repository traits belong in an application-facing port module so core does not depend on rusqlite.

```rust
pub struct ProjectId(Uuid);
pub struct SceneId(Uuid);
pub struct StructuralNodeId(Uuid);
pub struct PlotlineId(Uuid);

pub struct SceneDraft {
    pub title: String,
    pub synopsis: String,
    pub status: SceneStatus,
    pub target_words: Option<u32>,
}

pub struct SceneView {
    pub id: SceneId,
    pub draft: SceneDraft,
    pub placement: Option<ScenePlacement>,
    pub actual_words: u32,
    pub plotlines: Vec<ScenePlotline>,
    pub characters: Vec<SceneCharacter>,
}

pub trait StoryRepository {
    fn create_scene(&mut self, input: SceneDraft) -> Result<SceneId>;
    fn get_scene(&self, id: SceneId) -> Result<Option<SceneView>>;
    fn move_scene(&mut self, id: SceneId, chapter: StructuralNodeId, position: usize) -> Result<()>;
    fn reorder_scene(&mut self, id: SceneId, position: usize) -> Result<()>;
    fn set_scene_plotlines(&mut self, id: SceneId, links: Vec<ScenePlotline>) -> Result<()>;
}

pub trait ManuscriptStore {
    fn read_scene(&self, id: SceneId) -> Result<ManuscriptDocument>;
    fn write_scene(&mut self, id: SceneId, expected_hash: Option<ContentHash>, doc: &ManuscriptDocument)
        -> Result<WriteOutcome>;
}
```

The concrete signatures may use async APIs later, but synchronous local SQLite and file operations are sufficient for the initial terminal prototype. Avoid carrying database row structs into UI state. Application use cases include `CreateProject`, `CreateScene`, `MoveScene`, `UpdateSceneMetadata`, `SaveSceneText`, `BuildOutline`, `BuildPlotGrid`, `PreviewImport`, and `CommitImport`.

`MoveScene` validates that the destination is a chapter, adjusts source and destination positions atomically, and returns the new placement. Any error leaves both orderings unchanged. `SaveSceneText` uses an expected hash so an external editor change becomes a conflict result rather than a lost update.

## 6. Analysis contracts

Analysis functions accept domain snapshots or repository query results and return typed reports. They do not mutate story facts.

```rust
pub enum WordAttributionPolicy {
    Overlap,
    EqualShare,
    AuthorShares,
}

pub struct PlotGrid {
    pub rows: Vec<PlotlineId>,
    pub columns: Vec<StructuralNodeId>,
    pub cells: Vec<PlotGridCell>,
    pub attribution: WordAttributionPolicy,
}
```

Counts derived from text should be computed by one shared tokenizer policy and stored only as rebuildable cache. Reports include policy and inclusion filters in their result metadata. Continuity diagnostics carry stable IDs, severity, explanation and the exact entity references that triggered them; incomplete facts yield warnings or unverified suggestions, not asserted errors.

## 7. Import architecture and early validation

Import adapters are read-only and translate sources into a common `ImportInventory` (documents, hierarchy, fields, links, files, source identifiers and warnings). A mapping plan maps inventory types/fields to target entities and records unresolved ambiguity. `CommitImport` writes to a new staging project/directory, validates counts and references, writes an import report, then marks the project ready. A failed import remains visibly incomplete or is removed from the target location; it must not appear as a successful project.

### 7.1 Scrivener

Before format support is claimed, inspect representative project packages and document tested Scrivener versions and content forms. Keep package parsing separate from model mapping. Preserve source binder identifiers and unsupported assets in provenance/attachments. Import does not overwrite or edit the source. Re-import requires an explicit policy (new project or matched update); default is a new project.

### 7.2 Ranperen spreadsheets

Treat the three reference spreadsheets as fixtures for importer design. Inventory sheets, headings, formulas, merged cells, hidden rows/columns and chart data before defining mappings. Spreadsheet row identity is not guaranteed, so preserve source workbook/sheet/row coordinates as provenance and use a deterministic import key only within a given source fingerprint. Report conflicting values across versions; do not silently choose one. Rebuild charts from normalized records where possible.

Importer acceptance fixtures should compare source-derived counts, recovered scene order, character/plot assignments, chronology and issue records. Importing spreadsheet and Scrivener data must exercise the same scene model and relationships as manual entry before substantial UI work begins.

## 8. Terminal navigation model

The terminal frontend has a persistent project context, workspace, selection and navigation history. A workspace is a projection of domain data, not a separate data store. Initial global workspaces: Dashboard, Outline, Cards, Editor, Plot Grid, Characters, Story Bible, Timeline, Analytics, Research, Issues and Search.

Suggested navigation rules:

- `Tab`/`Shift-Tab` moves focus within a workspace; `?` opens context help; `:` opens the command palette.
- A single global scene selection is retained when switching between Outline, Cards, Editor and analytical views.
- Enter opens the selected entity; Escape backs out one navigation level; Back/Forward traverse history.
- Outline and Cards commands call the same `MoveScene` use case. Analytical sorting/filtering only changes the view unless the user invokes an explicit manuscript reorder command.
- Hoist and filter state are presentation state and do not change stored hierarchy.
- Editor autosave displays saved, saving, or conflict/error state. Dirty text is never silently discarded during navigation.
- Narrow terminals switch to compact rows and detail panes rather than hiding the selected entity's identity or save state.

Keep key bindings configurable and avoid binding domain actions to a specific widget. A future desktop frontend can expose equivalent commands through menus, pointer gestures or shortcuts.

## 9. Migration, recovery and integrity

Migrations are forward-only and numbered. Backups use SQLite's online backup API, include manuscript files and are validated before publishing. On startup, validate schema version, foreign keys, known content paths and hashes. A repair/reconciliation screen lists missing, changed and untracked files with safe actions: adopt external file, restore from backup, keep both, or relink. Never resolve divergence by choosing a version automatically.

Deletion is soft archival for scenes and core story entities in the initial UI. Hard deletion is a separate maintenance operation after dependencies have been resolved. Scene file deletion follows a confirmed archive/export policy and is not coupled to ordinary outline removal.

## 10. Recommended implementation sequence

1. Create a Rust workspace with `story-core`, `story-storage`, `story-app`, `story-import` and the CLI; implement IDs, project, structural nodes, scenes, placements, content file store, durable journal, custom fields, migration 0001 and provenance.
2. Build non-UI use cases and acceptance tests for create/reopen/move/reorder, including rollback and file-conflict cases.
3. Inspect the Ranperen files and representative Scrivener packages; write inventory-only adapters and schema-model findings before finalizing optional metadata fields.
4. Implement plotline, character, event and issue relationships; validate importer mappings against real source records.
5. After Phase 1 acceptance, build the terminal outline and editor as clients of the use cases.
6. Add remaining analysis, continuity and export slices as their entities become available.

This ordering keeps import investigation early, as required by the SRS, while avoiding the cost of implementing the full importer before the core identity and relationship model has been exercised.

## 11. Approved invariants and test contracts

### Project ownership and identity

One project directory contains one `story.db`; entities are owned implicitly by that database and do not carry redundant `project_id` columns. `project.toml` contains an immutable UUID matching the sole `project.id` row. Opening rejects missing, duplicate, malformed or mismatched identity; it never repairs an identity silently. All content paths are relative to the project root and path resolution rejects traversal outside it. Relocation preserves identity and works because no absolute project paths are persisted.

### Database invariants

- `structural_node.position` and `scene_placement.position` are non-negative integers and unique among siblings, including root nodes. Root uniqueness uses `CREATE UNIQUE INDEX ... WHERE parent_id IS NULL` because a normal SQLite unique constraint does not make NULL values equal.
- Structural hierarchy is acyclic. Application validation walks ancestors; a recursive trigger rejects cycles for direct SQL updates.
- Scene placement references only a node whose kind is `chapter`. A trigger rejects placement into sections/groups and rejects changing a populated chapter to another kind. Foreign keys are enabled and verified for every connection.
- Structural and scene reorders use two-phase offset-and-compact updates in one `IMMEDIATE` transaction. This avoids SQLite's immediate UNIQUE checks during swaps/shifts. On any error the transaction rolls back to original positions.
- AuthorShares uses integer basis points (10,000 = 100%, one basis point = 0.01%). A complete scene allocation is validated atomically: every participating plotline has a share and total equals 10,000. Allocated integer word counts use floor division followed by deterministic largest-remainder distribution, ties by plotline UUID; totals always equal scene words.

### Metadata classification

| SRS scene field | Representation in Phase 1 | Status |
|---|---|---|
| Stable ID, title, synopsis, status | Typed `Scene` properties | Implemented |
| Act/section, chapter, manuscript order | Structural nodes + scene placement | Implemented |
| Planned words, actual words | Typed target; actual derived from content | Implemented |
| Purpose, goal, outcome | Typed scene properties | Implemented |
| Start/finish day/time and duration | Typed `StoryTime` start/end values | Implemented |
| POV, major/minor/off-camera characters | `scene_character` role relation | Implemented |
| Starting/finishing location | Typed nullable location foreign keys | Implemented |
| Plotline memberships and word shares | `scene_plotline` relation | Implemented |
| Narrative events | `story_event` and `scene_event` relation | Implemented |
| Plot points/story points | Narrative beat entity | Deferred migration |
| Objects/items and artefacts | Object and possession entities | Deferred |
| Internal/external/plot/personal conflict | Typed custom fields initially | Extensible metadata |
| Climax and consequences | Typed custom fields initially | Extensible metadata |
| Follow-up notes/questions | Issues and typed custom fields | Partial; issue entity deferred |
| Tags/categories/custom classification | Tags/custom field tables | Custom fields in Phase 1; tags deferred |
| Rich source-specific fields | Custom field definitions/values + provenance | Implemented foundation |

Custom fields have stable UUIDs, project-specific definitions, type, required/default constraints, enum options and relational reference targets. Values are stored in typed columns, not opaque JSON. Type changes require an explicit migration/conversion; incompatible existing values block the change. Every imported field is either mapped, retained as a custom field, or explicitly reported unsupported.

### Provenance schema and importer contracts

Phase 1 includes `import_run`, `import_source_item`, and `entity_provenance`. A run records source type, display path/identifier, SHA-256 source fingerprint, started/completed timestamps, status, warnings and unsupported content. Source items record stable source document IDs and optional sheet/row, item fingerprint, inventory type, raw field map and mapping decision. Provenance links destination entity type/ID and optional source field to source item; source identifiers are preserved verbatim. A unique `(run_id, source_document_id)` prevents duplicate inventory items; repeated fingerprints require an explicit repeat policy. Synthetic fixture tests exercise inventory and mapping interfaces. No real Ranperen or Scrivener fixture exists in this repository, so compatibility is unverified.

### Acceptance tests

1. **Project:** create/open/relocate preserves UUID; tampered or unrelated `project.toml` and database identity are rejected; newer schema is rejected without mutation.
2. **Ordering:** root positions reject duplicates; swaps/moves work under immediate uniqueness; invalid moves and injected transaction errors preserve all positions; cycle and non-chapter placement fail both through services and direct SQL.
3. **Write journal:** inject termination at every protocol boundary (partial temp, synced temp, prepared intent, pre-rename, post-rename, post-metadata commit, cleanup). Reopen/recover yields old or new complete content as dictated by journal, never truncated text; a third external hash preserves both versions and yields a conflict.
4. **Chronology:** known zero differs from unknown; negative ticks work; precision/bounds validate; interval overlap returns ambiguity; checked duration overflow errors.
5. **Relationships/allocation:** FK integrity, multiple memberships, atomic complete 10,000-basis-point validation, rejection below/above/incomplete allocations and deterministic word remainder totaling scene words.
6. **Custom metadata:** valid types/defaults/enums/entity references persist across save/reopen and scene movement; invalid typed values and dangling references reject.
7. **Provenance:** synthetic source fingerprint and source IDs/locations/field mappings/warnings round trip; duplicate records are detected; failed runs remain failed/incomplete; source fixture bytes remain unchanged.

## 12. Remaining open decisions

- Markdown subset versus a richer canonical document tree: prototype import/export against real Scrivener formatting before fixing the long-term model.
- Fictional calendar labels and conversion rules beyond canonical integer ticks: test with real source data and a non-Gregorian example.
- Embedded terminal editor: evaluate Rust components and external-editor workflow before selecting an editing engine.
- Sparse order keys: begin with transactional integer positions and revisit only if reorder cost is measurable.
- Desktop framework: defer until the core API and terminal workflows are validated.
- Git integration and snapshots: ensure project files remain usable in Git; defer application-managed history design.

Approved decisions in Sections 3.4, 3.5 and 11 are fixed for Phase 1. This document supersedes the v0.1 schema sketch where it conflicts with these decisions; v0.1 remains the historical review baseline.
