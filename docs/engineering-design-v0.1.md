# Writer's IDE — Engineering Design

**Version:** 0.1  
**Status:** Initial design for review  
**Basis:** Software Requirements Specification 0.1

This document turns the SRS into an initial Rust domain model, SQLite schema, module boundaries, service APIs and terminal navigation model. It is intended to guide a small vertical slice and early importer prototypes. It does not lock the project into a specific TUI editor, desktop framework, rich-text format or Scrivener version.

## 1. Design decisions

1. A scene is a durable domain entity. Its identity does not depend on its chapter, manuscript position or file name.
2. A scene's manuscript placement is represented by a chapter membership and an explicit order key. Chronology is separate optional data.
3. Relationships such as scene-to-plotline and scene-to-character use join entities so role, attribution and provenance can be recorded.
4. SQLite stores structured data and the canonical ordering. Prose is stored as UTF-8 Markdown files, addressed by a stable scene UUID in the database.
5. All mutations pass through application services and database transactions. Frontends do not issue domain SQL directly.
6. Importers first produce a read-only inventory and a mapping plan. Committing an import creates a new project and records source provenance; it never mutates the source.
7. Dates in a fictional chronology are not assumed to be Gregorian dates. The first schema supports sortable story-time values and explicit uncertainty; richer fictional calendars can be added behind the chronology API.

## 2. Workspace and crate responsibilities

Initial workspace (crate names are provisional):

```text
writers-ide/
├── Cargo.toml
├── crates/
│   ├── story-core/        # IDs, domain types, invariants, value objects
│   ├── story-storage/    # SQLite repositories, migrations, file store
│   ├── story-analysis/   # word budgets, plot/character matrices, reports
│   ├── story-continuity/ # deterministic diagnostics over supplied facts
│   ├── story-import/     # source adapters, inventory, mapping, import plan
│   ├── story-export/     # compilation and structured reports
│   ├── story-templates/  # project and planning templates
│   └── story-cli/        # command-line project operations
└── apps/
    └── terminal/         # Ratatui/Crossterm frontend; added in UI phase
```

Dependency direction: `story-core` has no dependency on persistence or presentation. Storage, analysis, continuity, import and export depend on core. The application layer (initially housed in the terminal crate or a later `story-app` crate) composes these services. UI widgets call use cases, not repositories. Avoid adding a separate crate until a boundary or reuse need is demonstrated.

## 3. Domain model

### 3.1 Identity and common fields

Externally addressable entities use UUIDs generated by the application and serialized as lowercase hyphenated strings. IDs are never derived from names, order or paths. Database rows use `TEXT` IDs to keep import/export and debugging straightforward. Every mutable primary entity has `created_at` and `updated_at` UTC timestamps; timestamps are audit metadata, not story chronology.

Core entity types:

| Entity | Purpose |
|---|---|
| Project | Project settings, title, target and schema-independent preferences |
| StructuralNode | Section/act, chapter or future grouping in the manuscript tree |
| Scene | Stable narrative unit, metadata and lifecycle state |
| Plotline | Main plot, subplot or other author-defined thread |
| Character | Person or other agent represented in the story |
| Location | Place hierarchy and descriptive information |
| StoryEvent | Fictional-world occurrence, independent of its representation in prose |
| ResearchItem | Note or reference with links to story entities |
| Issue | Author-managed question or task |
| CustomFieldDefinition / CustomFieldValue | Project-defined typed metadata |

Other entities (objects, world rules, relationships, knowledge claims, snapshots, attachments) are planned extension points and should not be flattened into scene text. Add them with their own IDs and join tables when implementing those phases.

### 3.2 Manuscript structure and scene identity

The initial hierarchy is `Project → Section → Chapter → Scene`, with Section optional. `StructuralNode` supports configured levels while retaining an explicit kind for common operations. A scene is not a structural node: it is linked to exactly one chapter at a time through `scene_placement`. This makes movement explicit and keeps the scene's stable identity independent of placement.

For the first release, a scene has one current manuscript placement. If alternate versions or multiple manuscript occurrences are later required, introduce occurrence/variant entities rather than duplicating the scene row. Reordering uses an integer `position` within a parent; a service renumbers affected siblings in one transaction. This is simple and deterministic for a single-author local project. Sparse fractional ordering is deferred until profiling demonstrates a need.

`StructuralNode` may carry an optional target word count. Scene target is stored on `Scene`; actual words are calculated from the prose file and cached with its content hash. Parent actual totals are derived, not authoritative stored values.

### 3.3 Scene relationships

- `scene_plotlines(scene_id, plotline_id, role, word_share, source)` allows multiple plotlines and attribution policy inputs.
- `scene_characters(scene_id, character_id, participation_role, notes)` distinguishes POV, major, minor, off-camera and mentioned participation.
- `scene_events(scene_id, event_id, relationship_kind, notes)` is many-to-many: one scene can depict several events and an event can span scenes.
- Scene starting and ending locations are nullable references on the scene (or a dedicated location participation table if more granular movement is needed).
- Plot points and story points should initially be records in a shared `narrative_beats` table with a required `kind`; they may link to a scene, plotline and/or event. This avoids confusing them with whole-world StoryEvents.
- Tags use normalized tag records and join tables. Custom fields use typed definitions and values, with validation at the application boundary.

No join row implies an analytical judgment. For example, multi-plot membership records author attribution; charts state whether they use overlap, equal split or author proportions.

### 3.4 Story time

Manuscript position is an integer sequence and never doubles as story time. The first chronology representation uses an optional `story_order` integer for relative ordering and optional start/end values stored as decimal ticks from a project-defined epoch, with an optional calendar identifier. Unknown, approximate and range-based times require explicit precision/bounds fields; null means unknown, not zero. Do not use SQLite date functions for fictional dates. A `StoryTime` Rust value object owns comparison and validation rules. The initial schema can evolve to richer calendar tables without changing scene or event identity.

Until fictional-calendar requirements are prototyped against the Ranperen sheets, absolute dates are imported as source text plus normalized sortable value where conversion is unambiguous. Ambiguous values remain source text and produce an import warning.

### 3.5 Prose storage

Canonical v0 prose is UTF-8 Markdown with a documented restricted syntax. Files are `manuscript/<scene-uuid>.md`; title and planning metadata remain in SQLite. A `scene_content` row records relative path, content hash, byte length, detected format and last indexed time. A file store API performs atomic write via a sibling temporary file and rename, then commits metadata. Since filesystem and SQLite cannot share a transaction, recovery scans reconcile hash/path state on open and report conflicts; they never silently replace divergent content.

Use a Markdown parser/serializer abstraction so a richer internal representation can be evaluated later. Preserve original imported RTF/HTML/RTF-derived data as attachments or import artifacts when lossless conversion is unavailable. Markdown export must not be treated as proof that every Scrivener formatting feature survived.

## 4. SQLite schema outline

Use SQLite foreign keys (`PRAGMA foreign_keys=ON`), WAL mode where supported, busy timeout, and numbered migrations in a `schema_migrations` table. Every connection must enable foreign keys. Store schema version separately from project content version. Use indexes for joins, search and order. FTS5 is optional at startup and must have a documented fallback if unavailable.

Illustrative core schema (types and checks are normative; minor SQL syntax may change during migration implementation):

```sql
CREATE TABLE project (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  author TEXT NOT NULL DEFAULT '',
  genre TEXT NOT NULL DEFAULT '',
  synopsis TEXT NOT NULL DEFAULT '',
  target_words INTEGER CHECK (target_words IS NULL OR target_words >= 0),
  settings_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE structural_node (
  id TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES structural_node(id) ON DELETE RESTRICT,
  kind TEXT NOT NULL CHECK (kind IN ('section','chapter','group')),
  title TEXT NOT NULL,
  position INTEGER NOT NULL CHECK (position >= 0),
  target_words INTEGER CHECK (target_words IS NULL OR target_words >= 0),
  status TEXT NOT NULL DEFAULT 'planned',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(parent_id, position)
);

CREATE TABLE scene (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL DEFAULT '',
  synopsis TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'idea',
  target_words INTEGER CHECK (target_words IS NULL OR target_words >= 0),
  purpose TEXT NOT NULL DEFAULT '',
  goal TEXT NOT NULL DEFAULT '',
  outcome TEXT NOT NULL DEFAULT '',
  start_location_id TEXT,
  end_location_id TEXT,
  archived_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE scene_placement (
  scene_id TEXT PRIMARY KEY REFERENCES scene(id) ON DELETE CASCADE,
  chapter_id TEXT NOT NULL REFERENCES structural_node(id) ON DELETE RESTRICT,
  position INTEGER NOT NULL CHECK (position >= 0),
  UNIQUE(chapter_id, position)
);

CREATE TABLE scene_content (
  scene_id TEXT PRIMARY KEY REFERENCES scene(id) ON DELETE CASCADE,
  relative_path TEXT NOT NULL UNIQUE,
  format TEXT NOT NULL DEFAULT 'markdown',
  sha256 TEXT,
  byte_length INTEGER NOT NULL DEFAULT 0 CHECK (byte_length >= 0),
  indexed_at TEXT
);

CREATE TABLE plotline (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  kind TEXT NOT NULL DEFAULT 'subplot',
  priority INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'planned',
  target_words INTEGER CHECK (target_words IS NULL OR target_words >= 0),
  intended_resolution TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE scene_plotline (
  scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  plotline_id TEXT NOT NULL REFERENCES plotline(id) ON DELETE RESTRICT,
  role TEXT NOT NULL DEFAULT 'advances',
  word_share REAL CHECK (word_share IS NULL OR (word_share >= 0 AND word_share <= 1)),
  PRIMARY KEY(scene_id, plotline_id)
);

CREATE TABLE character (
  id TEXT PRIMARY KEY,
  full_name TEXT NOT NULL,
  preferred_name TEXT NOT NULL DEFAULT '',
  description TEXT NOT NULL DEFAULT '',
  background TEXT NOT NULL DEFAULT '',
  goals TEXT NOT NULL DEFAULT '',
  motivations TEXT NOT NULL DEFAULT '',
  secrets TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE scene_character (
  scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  character_id TEXT NOT NULL REFERENCES character(id) ON DELETE RESTRICT,
  participation_role TEXT NOT NULL CHECK (participation_role IN
    ('pov','major','minor','off_camera','mentioned')),
  notes TEXT NOT NULL DEFAULT '',
  PRIMARY KEY(scene_id, character_id, participation_role)
);

CREATE TABLE location (
  id TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES location(id) ON DELETE RESTRICT,
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE story_event (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  time_start REAL,
  time_end REAL,
  time_precision TEXT NOT NULL DEFAULT 'unknown',
  source_time_text TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  CHECK (time_end IS NULL OR time_start IS NULL OR time_end >= time_start)
);

CREATE TABLE scene_event (
  scene_id TEXT NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
  event_id TEXT NOT NULL REFERENCES story_event(id) ON DELETE RESTRICT,
  relationship_kind TEXT NOT NULL DEFAULT 'depicts',
  PRIMARY KEY(scene_id, event_id, relationship_kind)
);
```

Additional tables to add with their implementation slices:

- `narrative_beat`, `scene_narrative_beat`, `plotline_narrative_beat`.
- `tag`, `scene_tag`, plus typed custom-field definition/value tables.
- `research_item`, `research_link`, `issue`, and explicit issue link tables.
- `character_relationship`, `character_knowledge`, `story_object`, `object_transfer`, `world_rule`.
- `import_run`, `import_source_item`, `entity_provenance` for repeatable, inspectable imports.
- `scene_fts` and other FTS virtual tables, updated transactionally or via rebuildable indexing hooks.

Do not use polymorphic `entity_type/entity_id` foreign-key pairs for core relationships where a real foreign key can be maintained. For cross-type research links, use a typed link table per target kind or accept and validate a polymorphic edge in the application layer with explicit integrity checks.

## 5. Rust API boundaries

The domain model exposes value types and invariants. Repository traits belong in an application-facing port module so core does not depend on rusqlite.

```rust
pub struct ProjectId(Uuid);
pub struct SceneId(Uuid);
pub struct StructuralNodeId(Uuid);
pub struct PlotlineId(Uuid);

pub struct SceneDraft {
    pub title: String,
    pub synopsis: String,
    pub status: SceneStatus,
    pub target_words: Option<u32>,
}

pub struct SceneView {
    pub id: SceneId,
    pub draft: SceneDraft,
    pub placement: Option<ScenePlacement>,
    pub actual_words: u32,
    pub plotlines: Vec<ScenePlotline>,
    pub characters: Vec<SceneCharacter>,
}

pub trait StoryRepository {
    fn create_scene(&mut self, input: SceneDraft) -> Result<SceneId>;
    fn get_scene(&self, id: SceneId) -> Result<Option<SceneView>>;
    fn move_scene(&mut self, id: SceneId, chapter: StructuralNodeId, position: usize) -> Result<()>;
    fn reorder_scene(&mut self, id: SceneId, position: usize) -> Result<()>;
    fn set_scene_plotlines(&mut self, id: SceneId, links: Vec<ScenePlotline>) -> Result<()>;
}

pub trait ManuscriptStore {
    fn read_scene(&self, id: SceneId) -> Result<ManuscriptDocument>;
    fn write_scene(&mut self, id: SceneId, expected_hash: Option<ContentHash>, doc: &ManuscriptDocument)
        -> Result<WriteOutcome>;
}
```

The concrete signatures may use async APIs later, but synchronous local SQLite and file operations are sufficient for the initial terminal prototype. Avoid carrying database row structs into UI state. Application use cases include `CreateProject`, `CreateScene`, `MoveScene`, `UpdateSceneMetadata`, `SaveSceneText`, `BuildOutline`, `BuildPlotGrid`, `PreviewImport`, and `CommitImport`.

`MoveScene` validates that the destination is a chapter, adjusts source and destination positions atomically, and returns the new placement. Any error leaves both orderings unchanged. `SaveSceneText` uses an expected hash so an external editor change becomes a conflict result rather than a lost update.

## 6. Analysis contracts

Analysis functions accept domain snapshots or repository query results and return typed reports. They do not mutate story facts.

```rust
pub enum WordAttributionPolicy {
    Overlap,
    EqualShare,
    AuthorShares,
}

pub struct PlotGrid {
    pub rows: Vec<PlotlineId>,
    pub columns: Vec<StructuralNodeId>,
    pub cells: Vec<PlotGridCell>,
    pub attribution: WordAttributionPolicy,
}
```

Counts derived from text should be computed by one shared tokenizer policy and stored only as rebuildable cache. Reports include policy and inclusion filters in their result metadata. Continuity diagnostics carry stable IDs, severity, explanation and the exact entity references that triggered them; incomplete facts yield warnings or unverified suggestions, not asserted errors.

## 7. Import architecture and early validation

Import adapters are read-only and translate sources into a common `ImportInventory` (documents, hierarchy, fields, links, files, source identifiers and warnings). A mapping plan maps inventory types/fields to target entities and records unresolved ambiguity. `CommitImport` writes to a new staging project/directory, validates counts and references, writes an import report, then marks the project ready. A failed import remains visibly incomplete or is removed from the target location; it must not appear as a successful project.

### 7.1 Scrivener

Before format support is claimed, inspect representative project packages and document tested Scrivener versions and content forms. Keep package parsing separate from model mapping. Preserve source binder identifiers and unsupported assets in provenance/attachments. Import does not overwrite or edit the source. Re-import requires an explicit policy (new project or matched update); default is a new project.

### 7.2 Ranperen spreadsheets

Treat the three reference spreadsheets as fixtures for importer design. Inventory sheets, headings, formulas, merged cells, hidden rows/columns and chart data before defining mappings. Spreadsheet row identity is not guaranteed, so preserve source workbook/sheet/row coordinates as provenance and use a deterministic import key only within a given source fingerprint. Report conflicting values across versions; do not silently choose one. Rebuild charts from normalized records where possible.

Importer acceptance fixtures should compare source-derived counts, recovered scene order, character/plot assignments, chronology and issue records. Importing spreadsheet and Scrivener data must exercise the same scene model and relationships as manual entry before substantial UI work begins.

## 8. Terminal navigation model

The terminal frontend has a persistent project context, workspace, selection and navigation history. A workspace is a projection of domain data, not a separate data store. Initial global workspaces: Dashboard, Outline, Cards, Editor, Plot Grid, Characters, Story Bible, Timeline, Analytics, Research, Issues and Search.

Suggested navigation rules:

- `Tab`/`Shift-Tab` moves focus within a workspace; `?` opens context help; `:` opens the command palette.
- A single global scene selection is retained when switching between Outline, Cards, Editor and analytical views.
- Enter opens the selected entity; Escape backs out one navigation level; Back/Forward traverse history.
- Outline and Cards commands call the same `MoveScene` use case. Analytical sorting/filtering only changes the view unless the user invokes an explicit manuscript reorder command.
- Hoist and filter state are presentation state and do not change stored hierarchy.
- Editor autosave displays saved, saving, or conflict/error state. Dirty text is never silently discarded during navigation.
- Narrow terminals switch to compact rows and detail panes rather than hiding the selected entity's identity or save state.

Keep key bindings configurable and avoid binding domain actions to a specific widget. A future desktop frontend can expose equivalent commands through menus, pointer gestures or shortcuts.

## 9. Migration, recovery and integrity

Migrations are forward-only and numbered. Backups include the database and manuscript tree from a consistent application-controlled checkpoint. On startup, validate schema version, foreign keys, known content paths and hashes. A repair/reconciliation screen lists missing, changed and untracked files with safe actions: adopt external file, restore from backup, keep both, or relink. Never resolve divergence by choosing a version automatically.

Deletion is soft archival for scenes and core story entities in the initial UI. Hard deletion is a separate maintenance operation after dependencies have been resolved. Scene file deletion follows a confirmed archive/export policy and is not coupled to ordinary outline removal.

## 10. Recommended implementation sequence

1. Create a Rust workspace with `story-core` and `story-storage`; implement IDs, project, structural nodes, scenes, placements, content file store and migrations.
2. Build non-UI use cases and acceptance tests for create/reopen/move/reorder, including rollback and file-conflict cases.
3. Inspect the Ranperen files and representative Scrivener packages; write inventory-only adapters and schema-model findings before finalizing optional metadata fields.
4. Implement plotline, character, event and issue relationships; validate importer mappings against real source records.
5. Build the terminal outline and editor as clients of the use cases.
6. Add analysis, continuity and export slices as their entities become available.

This ordering keeps import investigation early, as required by the SRS, while avoiding the cost of implementing the full importer before the core identity and relationship model has been exercised.

## 11. Open decisions retained

- Markdown subset versus a richer canonical document tree: prototype import/export against real Scrivener formatting before fixing the long-term model.
- Fictional calendar semantics and uncertainty representation: test against Ranperen data and a non-Gregorian example.
- Embedded terminal editor: evaluate Rust components and external-editor workflow before selecting an editing engine.
- Sparse order keys: begin with transactional integer positions and revisit only if reorder cost is measurable.
- Desktop framework: defer until the core API and terminal workflows are validated.
- Git integration and snapshots: ensure project files remain usable in Git; defer application-managed history design.
